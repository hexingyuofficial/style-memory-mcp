# v0.5.0 实施窗口提示词

将下面整段粘贴到新的实施窗口。

```text
你正在实施 style-memory-mcp v0.5.0。

工作区：
/absolute/path/to/style-memory-mcp

首先完整阅读：
1. docs/V0.5.0-HARDENING-PLAN.zh-CN.md
2. docs/V0.5.0-EXECUTION-PLAN.zh-CN.md
3. docs/V0.5.0-IMPLEMENTATION-PROMPT.zh-CN.md
4. CONTRIBUTING.md
5. 与当前阶段有关的现有源码和测试

不要只根据这段提示词实现。
V0.5.0-HARDENING-PLAN.zh-CN.md 是产品契约和验收真源，
V0.5.0-EXECUTION-PLAN.zh-CN.md 是强制执行顺序。

目标：
将现有 v0.4.0 的零散 style habits 升级为安全、可迁移的 v2 风格记忆，
最终 brief 使用六段结构：称呼、核心语感、口癖、标点与表情、陪伴偏好、翻车日志。
在关键行为稳定性不下降的前提下，最小化完整对话的 LLM token 总成本；必须计入工具 schema、
调用参数、工具返回、首次 capsule 和后续 delta，不能只优化 brief 字数。
安装新版本时必须能自动替换旧程序，保留 store 和宿主配置，
任意阶段失败都能回滚。

不可变条件：
- 不得从环境、其他开发者或文档示例推断用户称呼。
- 称呼必须双向记录且显式保存 from/to，只允许 user→assistant 和 assistant→user。
- 两个方向是完全独立的命名空间：同一个 literal 可以双向并存，拥有独立 id、状态、证据和摘要；
  confirm/correct/forget/archive/pin 任一方向时，另一个方向的同 literal 必须保持不变。
- user→assistant 表示用户怎样叫 agent，只识别、绝不反过来称呼用户。每个 active 项带一句短的
  可观察情绪/关系语境，例如亲昵、玩笑或想拉近距离；证据不足时使用中性摘要，不能猜心理或人格。
- assistant→user 才是 agent 可以怎样叫用户。它只能来自用户明确要求/确认，或多次无歧义表达
  “你可以这样叫我”；assistant 自己曾这样叫用户不能成为学习证据，禁止输出自我强化。
- 引用、转述、否定、反例、第三方/角色姓名、文档示例、环境文本、工具输出和 assistant 消息
  不得成为称呼证据。称呼 hint 必须绑定当前用户消息并携带合法方向。
- 称呼 store 每方向最多 6 个，brief 每方向典型 1 个、最多 2 个；满容量时拒绝自动候选并报告，
  不能静默删除。称呼不参加表达模式的 30/180/360 天自动遗忘。
- 不分“技术风格”和“闲聊风格”两套人设。产品重点是闲聊和情感陪伴。
- 用户自己的语感 observedVoice 与用户希望 agent 如何回应 responsePreferences 必须分开。
- 用户说得短不等于 agent 应该回得短。
- 不使用 temperature 表示情绪。用户表达强度是 expressiveness，agent 回应温度是 warmth。
- 1-5 数值注入时必须附固定语义标签，如“回复长度=3/5（正常展开）”，不输出裸数字。
- 口癖是重点，但主记录必须是 `ExpressionPattern`，而不是 literal 清单。每项包含
  `kind + behaviorSummary + functions + variationPolicy`；用户实际使用的词、颜文字或 emoji
  只放在 `examples`/证据中，brief 通常只带一个例子。
- `variationPolicy` 只有 `exact_only/same_family/open_variation`：固定口头禅和特殊标点可要求原样；
  颜文字、emoji、笑声可在同类型、同功能、同强度内换用未见过的同类；不得漂移到无关表达。
- store 最多保留 12 个未固定 active 表达模式；典型 brief 选择 2 个，硬上限 5 个，
  每个只带一个代表例子。5 是上限而非目标，capsule token 上限优先，不能为了凑满而突破预算。
- 单条回复通常只自然使用 0-1 个模式，不能机械复读最近看到的原文；情境变化时应选择相关模式，
  不能让同一组长期固定霸占 brief。
- 文档中“确实/哈哈哈哈/好家伙”等只是格式示例，不是默认用户记忆，不得自动写入。
- 表达模式支持词语、笑声、emoji、颜文字、Unicode 符号、文本标记、中英混用和未来类型；
  外部仍按六段格式渲染到“口癖”或“标点与表情”，同一模式不重复。
- 。。。、...、……、?!、？！、~~ 等特殊标点必须原样存储和渲染，不归一化。
- 普通观察使用滚动估计+滞回，不能每条消息对整数分值直接 +1/-1。
- 明确用户反馈优先；某种表达在一条消息中缺席不是反证。
- 比较完整六段、active-only 紧凑六段和“紧凑 capsule + delta”，在行为达标方案中选总 token 最少者。
- 初始发布上限：典型 capsule <=120 tokens，全上限 <=240，普通 delta <=30；按目标模型 tokenizer 验证。
- brief 使用 revision；未变化不重复正文，普通变化发 delta，纠错、上下文压缩或无法独立执行时才刷新完整 capsule。
- hook 通道在模型外逐消息 observe，不产生模型工具调用；无 hook 时使用 agent 通道：冷启动
  需要精确统计则按 `full` 逐消息调用，核心记忆成熟后转 `event`，只在明确反馈、纠正、
  疑似已知模式、新例子或特殊表达实际出现时调用；`off` 只读。bootstrap/status 必须返回 channel 和 policy。
- 宿主只附紧凑语义 hint，最终评分由 MCP 决定；未提交的消息不能补算。session 末蒸馏候选
  最多贡献 1 次低权重观察，不接受批量 count，不绕过表达模式 3 次、2 个 session 的门槛。
- MCP 本身没有 LLM：规则提取只能生成 `kind + literal` 的低层证据；细微的行为功能和变体边界
  必须来自明确用户反馈、已有模式匹配或宿主提供的紧凑语义 hint，不能凭一个符号乱猜。
- 简单遗忘必须沿用 `candidate -> active -> archived -> deleted`：candidate 30 天无新证据删除，
  active 180 天无新证据归档，archived 从最后出现起 360 天删除。pinned 不自动遗忘，forget 立即删除。
- 默认 store 未固定项容量为 active/candidate/archived = 12/24/24，总安全上限 64。超限按
  `pinned > explicit > sessionCount > seenCount > lastSeenAt > stableId` 确定性处理；全 protected 时拒绝自动学习并报告。
- archived 重现后只计算归档后的新证据，重新满足 3 次、2 个 session 才 active；明确确认可立即恢复。
- 自动遗忘仅作用于表达模式，绝不能因长期未出现而忘掉称呼、明确陪伴偏好或翻车日志。
- 默认聊天连接最多暴露 3 个 runtime 工具，admin 工具按需启用；日常成功返回只含紧凑 ack/refresh。
- 20 回合成本必须使用实际模型 usage，计入每轮 input/output、工具 schema、调用参数/返回、capsule/delta，
  以及 capsule 留在后续上下文中的输入；cached input 单列，不能把“只注入一次”误写成只花一次 token。
- 跨 session 必须依赖持久 MCP 配置、固定绝对 STYLE_MEMORY_PATH 和宿主全局 agent 指令，不能依赖某个聊天窗口记住规则。
- 新 session 首轮实质回复前读取 brief；使用无语义短 sessionId 区分证据，优先由宿主集成层自动提供。
- store v1 -> v2 迁移必须备份、幂等、原子替换，失败时原 store 不变。
- 自动替换旧程序必须通过 E10 的并发和 fault-injection 回滚实验。

工作方式：
1. 立即创建一个持久 Goal，目标写明：完成 S1-S8、SM-050-01 至 SM-050-10、E01-E10、
   全量验证和最终 Sol review，全部翻绿且无遗留问题；不 commit、不发布、不修改真实安装。
   在所有结束门槛满足前保持 Goal active，不得因阶段测试通过或 token 预算临近而提前 complete。
2. 你是唯一实施和集成负责人，预期模型为 gpt-5.6-luna、reasoning=xhigh。先检查 git status，
   阅读现有改动，不覆盖用户已有改动；再运行基线 npm test、npm run check、npm run build。
3. 严格按执行计划 S1 -> S8 顺序，一次只做一个阶段。每阶段先写旧行为会失败的测试，
   再完成实现；亲自检查全部 diff、运行定向实验和要求的回归命令，证据齐全才逐项翻绿。
4. 你最多可以创建一个 gpt-5.6-luna、reasoning=medium 的低等级 worker，并在后续阶段复用；同一时刻最多一个
   worker 活跃。只派发单个边界明确的小任务，指定允许修改的文件和验收命令。worker 不得再拉 agent、
   不得改计划状态、不得安装/发布/提交，也不得与你并发修改同一文件。你必须亲自复核其全部改动。
5. 本地实现阶段不要创建 reviewer。任何实验失败都由你继续修复并重跑；不得删除测试、skip、
   改弱断言、扩大超时、修改验收条件，或用摘要代替可复现证据。
6. S1-S8、SM-050-01 至 SM-050-10、E01-E10 本地全部翻绿后，你再亲自运行一次最终全量命令，
   核对完整 diff、状态、证据索引和隔离安装边界。
7. 只有步骤 6 通过后，创建一个最高等级 gpt-5.6-sol reviewer，使用环境允许的最高 reasoning effort。
   reviewer 只读，不允许编辑；要求其独立阅读三份计划、完整 diff、源码、测试、E01-E10 证据和 token 报告，
   按严重度列 findings，不信任你的摘要。
8. reviewer 有任何 finding，就把受影响的 S/SM/E 项退回白色，由你修复并重跑受影响实验和全部最终命令；
   然后向同一个 reviewer 发 follow-up 复查。必须复用这个 reviewer，不要创建多个 reviewer。
9. 持续执行“修复 -> 自验 -> 同一 reviewer 复查”循环，直到 reviewer 明确无遗留 findings、
   所有状态重新为绿色。此时记录终审证据、将 Goal 标记 complete，并停在未提交状态。

模型边界：
- 如果 gpt-5.6-luna 或指定 reasoning 在当前环境不可用，记录实际模型，不得假称已使用。
- 如果最高等级 gpt-5.6-sol reviewer 不可用，不得标绿终审或完成 Goal；保留现场并报告阻塞。
- 不得为了“多看一遍”额外创建 worker/reviewer；一个可复用 worker 加一个可复用最终 reviewer 是硬上限。

跨 session 验收不能只重启同一个进程。至少创建 3 个独立 session，证明宿主能自动启动 MCP、
首轮从同一 store 读取一致 brief；hook 通道持续自动写回，agent 通道分别按 full/event/off 验收，
并且 sessionId 能正确区分跨会话证据。通道与策略必须明确标注，不得混称。

- 输出文件变更、兼容性、实验证据、reviewer 记录和剩余风险。

禁止：

- 不要直接修改用户真实 agent 的现有安装或真实 store；E10 使用隔离 fixture/sandbox。
- 不要在任何计划项仍是白色、实验未通过或 reviewer 有遗留问题时结束。
- 不要让 worker 或 reviewer 执行 commit、push、tag、publish、真实安装或破坏性 Git 操作。

完成后停在未提交状态。用户会将整个工作树交给另一个独立窗口审核，
独立审核通过后再由用户授权 Git 提交。
```
