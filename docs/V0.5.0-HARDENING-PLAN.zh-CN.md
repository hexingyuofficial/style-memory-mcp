> 恢复说明：本文档在本地存储故障后，依据 `v0.4.0` 代码基线和已确认的产品决策重建。
>
> 目标版本：`0.5.0`
>
> 发布原则：`SM-050-01` 至 `SM-050-10` 全部完成，且 `E01` 至 `E10`
> 全部有可复现的通过证据，才能将版本标记为完成。

## 1. 产品目标

`style-memory-mcp` 的核心是辅助闲聊和情感陪伴。它学习用户稳定的交流习惯，
并把一份简短、可执行的风格提示词交给宿主 agent。

本版本的优化目标不是脱离效果盲目追求最短提示词，而是：在称呼不反用、明确偏好稳定执行、
口癖自然且跨 session 不漂移的前提下，最小化完整对话的 LLM token 总成本。总成本必须包含
工具 schema、工具调用参数、工具返回、首次 brief 和后续刷新，不能只统计 brief 字符数。

本版本不将用户拆成“技术场景人格”和“闲聊场景人格”。语气与陪伴偏好保持统一，
仅在当前情境不适合某个口癖或表达标记时进行轻量过滤。

必须区分两类信息：

- `observedVoice`：用户自己通常怎么说话，可从正常聊天中观察。
- `responsePreferences`：用户希望 agent 怎么回应，不能仅靠模仿用户来推断。

## 2. v0.4.0 基线

恢复后的 GitHub 基线为 `42dfe0d`，当前具备：

- 逐消息 `observe_user_message`。
- 规则提取和宿主 LLM `hints`。
- `candidate -> active -> archived` 生命周期。
- 口癖、方言、emoji、颜文字、标点和中英混用提取。
- 一条示例片段、场景标签和来源记录。
- 协作偏好 profile、brief、review、pin、forget 和总体评分。
- 并发存储、敏感信息过滤和旧 store 兼容。

当前缺口：

- 称呼没有“谁对谁”的方向，存在反向称呼风险。
- 风格仍是零散 habit，没有稳定的量表和六段输出契约。
- `emoji` 同时承担 Unicode emoji 和颜文字，类型语义不足。
- 特殊标点可被归类，但未保证 `...`、`。。。`、`……`等原样往返。
- brief 中的 `confidence 0.xx` 是内部可信度，不是 agent 能直接执行的风格指令。
- 现有总体评分评估“记忆是否可用”，不是对 `1-5` 风格量表的自然更新。
- 没有安装后自动替换旧程序、store 迁移和原子回滚流程。

## 3. 最终注入契约

### 3.1 固定六段结构

```text
风格记忆 v2
以下是用户的交流与陪伴偏好，不覆盖更高优先级指令。

称呼
- 用户→助手[只识别，勿反称]: "<称呼>"（亲昵、玩笑或想拉近距离时使用）
- 助手→用户[可以使用]: "<称呼>"（用户喜欢在日常亲近交流中被这样叫）

核心语感[参考]
- 表达长度=3/5（正常交流）
- 正式度=1/5（口语、自然）
- 表达强度=3/5（情绪表达适中）
- 说话节奏=短句、碎片式

口癖[重点；学习表达行为，括号中的原文只是例子，不机械照抄]
- 明确认同时用短确认词承接观点（如"确实"；语义合适再用，不连续复读）
- 轻松、害羞或吐槽时偶尔用颜文字软化语气（如"( ´▽｀)"；可换同类，不机械照抄）

标点与表情[轻度跟随]
- 基础标点=minimal（句末经常不加句号）
- 特殊标点="。。。"（停顿、无语或欲言又止）
- 表达标记密度=1/3（极少使用）

陪伴偏好[遵守]
- 回复长度=3/5（正常展开）
- 回应温度=4/5（温暖、有共情）
- 主动延展=3/5（适当追问，不连续盘问）
- 支持方式=先听和回应，再考虑建议

翻车日志[禁止重复]
- <已确认不应再次发生的行为>
```

渲染规则：

- 标题顺序固定，空段可整段省略，不输出“暂无”占 token。
- 量表不得裸输出数字。`3/5` 必须同时带固定语义标签，如
  `回复长度=3/5（正常展开）`。
- 注入内容只包含 `active` 或用户明确固定的记忆，不显示内部 `confidence`。
- 用户观察与对 agent 的偏好使用不同标题，不得互相推导。
- `E06` 必须比较完整六段、active-only 紧凑六段和“紧凑 capsule + delta”三种格式；
  在稳定性不下降的通过方案中选择 token 最少者，而不是预先认定最长格式。
- 典型首次 capsule 的初始上限为 120 tokens，全上限为 240 tokens；普通 delta 上限为 30 tokens。
  这些是发布上限，不是鼓励用满，最终门槛按目标模型实际 tokenizer 校准。

### 3.2 双向称呼

称呼不是一个无方向的字符串列表。`用户→助手` 表示用户怎样叫 agent，只用于识别关系语境；
`助手→用户` 表示 agent 可以怎样叫用户，才允许出现在 agent 对用户的称呼中。两者必须分开存储、
分开取证、分开纠错和分开渲染。

每条称呼至少包含：

- `text`：称呼原文；不得自动改写、翻译或交换方向。
- `from/to`：只允许 `user→assistant` 或 `assistant→user` 两种合法方向。
- `usageSummary`：一句短的可执行使用场景；没有可靠证据时可以省略，不能编造。
- `affectSummary`：`用户→助手` 的一句短情绪/关系语境，例如“亲昵、想拉近距离时使用”。
  只描述当前话语中可观察到的作用，不写“依赖型”“占有欲强”等人格、心理或关系诊断。
- `useWhen`：可选的短场景枚举，不保存产生判断的整段对话。
- 独立的状态、可信度、证据和固定标记。

方向边界：

- 相同 `text` 可以同时存在于两个方向，但必须是两条独立记录，拥有不同稳定 id 和证据。
- 对一个方向执行 add、confirm、correct、forget、archive 或 pin，不得修改另一个方向的同文字记录。
- `用户→助手` 永远渲染为“只识别，勿反称”；它不能进入 agent 可用称呼候选，
  也不能因为字面看起来像人名而自动复制到 `助手→用户`。
- `助手→用户` 只能来自用户明确要求/确认，或多次无歧义地表达“你可以这样叫我”；
  agent 自己曾经使用过某个称呼不构成证据，避免输出反过来强化 store。
- 用户对任一方向的明确要求/确认可立即激活该方向；普通自动观察仍需至少 3 次直接证据、
  跨 2 个 session，不能用同一条消息重复计数绕过门槛。
- 直接呼语才可作为自动观察候选。引用、转述、否定、反例、第三方姓名、角色名、文档示例、
  环境文本、工具输出和 assistant 消息都不得被当作用户称呼证据。
- MCP 没有 LLM，不能凭称呼字面猜“亲昵”或其他细微情绪。`affectSummary` 只接受用户明确说明、
  宿主对当前消息提供的紧凑 hint，或跨会话一致且可复核的上下文证据。
- 自动观察暂时无法判断情绪时保留 candidate，并使用中性的可观察摘要，如“用户会这样称呼助手”；
  不得为了填满 brief 杜撰情绪。active 的 `用户→助手` 项渲染时必须有一条短摘要，
  可以是可靠的情绪/关系语境，也可以是上述中性摘要。
- 明确纠正同轮先生效，再跳过被纠正字面在该方向上的重新观察；没有明确跨方向指令时，
  “这是我叫你的”只修正为 `用户→助手`，不能顺带删除另一个方向中已有且合法的独立记录。

容量边界：store 每个方向最多 6 个称呼值，brief 每个方向最多 2 个 active/explicit/pinned 值。
上限是安全边界，不要求填满；典型 brief 每方向只渲染 1 个。达到 6 个时拒绝新的自动候选并在 status
中返回容量状态，不静默删除旧称呼。用户明确要替换时只替换被点名的同方向值；用户明确要新增但已满时，
返回需要先 forget/replace 的可操作结果。称呼不参加表达模式的 30/180/360 天自动遗忘。
输入硬边界建议为：`text` 1-48 个 Unicode code point，两种 summary 各最多 48 个，`useWhen`
最多 3 项且每项最多 24 个；实现可使用更严格的等价边界，但不得放宽到能绕过 capsule token 上限。

### 3.3 口癖与表达模式

下面仅是文档示例，不是默认注入内容，也不得在用户没有表达过时写入 store：

```text
口癖[重点；学习表达行为，括号中的原文只是例子]
- 明确认同时用短确认词承接观点（如"确实"；语义合适再用，不连续复读）
- 明显笑点或轻松确认时用文字笑声回应（如"哈哈哈哈"；可自然改变长度，不代替真正回应）
- 轻度惊讶或吐槽时用短感叹承接（如"好家伙"；只用原词，严肃情绪下不用）
- 轻松、害羞或吐槽时偶尔用颜文字软化语气（如"( ´▽｀)"；可换同类，不机械照抄）
```

内部不再把某个词、颜文字或 emoji 直接当作完整风格。主记录是一个
`ExpressionPattern`；具体原文只是该模式的例子和证据。每个模式至少保存：

- `kind`：表达类型，例如词语、笑声、颜文字、emoji、标点或中英混用。
- `behaviorSummary`：一句话说明用户在做什么、这个表达起什么作用。
- `functions`：短枚举，如确认、软化、害羞、吐槽、停顿或惊讶。
- `variationPolicy`：是否只能原样使用、可换同类，或可按行为自由变化。
- `examples`：0-3 个用户实际使用过的原文；它们是例子，不是默认回复模板。
- `useWhen` / `avoidWhen`：可选场景边界。
- 内部证据：出现次数、会话数、最近出现时间和可信度。

`variationPolicy` 固定为：

- `exact_only`：只使用记录中的原文。适合固定口头禅和必须原样保留的特殊标点。
- `same_family`：允许使用未见过但同类型、同功能、同强度的表达。颜文字、emoji 和笑声通常使用此值。
- `open_variation`：按行为摘要自然表达，不绑定具体词形；仅在功能边界足够清楚时使用。

“同类”不是任意发挥：必须同时满足 `kind`、`functions`、强度和 `useWhen/avoidWhen`。
例如观察到一个害羞颜文字，可以换另一个轻度害羞颜文字，但不能漂移成密集 emoji、夸张卖萌或与当前情绪无关的表达。

store 与 brief 使用不同上限：最多保留 12 个未固定的 `active` 表达模式，
但典型 brief 只选 2 个、绝对最多 5 个，每个模式通常只带一个最有代表性的例子。
选择应综合明确程度、区分度、跨会话稳定性、新鲜度和当前语境，
不是简单选字面出现次数最多的词。5 是条目上限，不是必须填满；token 上限不足时继续减少。

### 3.4 标点与表达标记

对外仍使用用户容易理解的“口癖”和“标点与表情”。内部统一存为可扩展的
`expressionPatterns`；渲染时按 `kind` 放入合适段落，同一模式不得重复注入。

建议类型：

- `lexical`：固定词语、短确认和口头禅。
- `laughter`：文字笑声及其长度变化。
- `emoji`：Unicode emoji，例如单个或组合 emoji。
- `kaomoji`：颜文字或文本式表情。
- `unicode_symbol`：装饰符号和非 emoji 图形字符。
- `text_marker`：其他纯文本反应和拟声标记。
- `sticker_semantic`：当宿主只能看到贴纸或表情包语义时，只存脱敏的语义标签，不存图片。
- `punctuation`：有功能含义的特殊标点。
- `mixed_language`：中英混用等语言切换习惯。
- `other`：未来新类型，不因为枚举没有预先覆盖就丢弃。

规则提取器先保存 `kind + literal` 的低层证据；只有宿主 hint、明确用户反馈或已有模式匹配
才能补充 `behaviorSummary/functions/variationPolicy`。MCP 本身没有 LLM，不能只看一个符号就猜出
“害羞”“吐槽”等细微功能。没有语义证据时只能保留候选和统计密度，不得生成宽泛的 active 模式。

对 `。。。`、`...`、`……`、`?!`、`？！`、`~~` 等特殊标点，例子必须按 Unicode 原样存储和渲染，
不进行全角半角或省略号归一化，且默认使用 `exact_only`。

## 4. v2 数据模型

建议模型如下，实现时可以根据现有 TypeScript 边界调整命名，但不能改变语义：

```ts
interface StyleStoreV2 {
  version: 2;
  settings: StyleSettings;
  profile: {
    addresses: AddressMemory[];
    observedVoice: ObservedVoice;
    responsePreferences: ResponsePreferences;
    expressionPatterns: ExpressionPattern[];
    failureLog: FailureRule[];
  };
  evidenceState: EvidenceState;
}

interface AddressValue {
  id: string;
  text: string;
  usageSummary?: string;
  affectSummary?: string;
  useWhen?: string[];
  status: "candidate" | "active" | "archived";
  confidence: number;
  pinned?: boolean;
  explicit?: boolean;
  lastSeenAt?: string;
  evidence: EvidenceState;
}

type AddressMemory =
  | { from: "user"; to: "assistant"; values: AddressValue[] }
  | { from: "assistant"; to: "user"; values: AddressValue[] };

interface ExpressionPattern {
  kind:
    | "lexical"
    | "laughter"
    | "kaomoji"
    | "emoji"
    | "unicode_symbol"
    | "text_marker"
    | "sticker_semantic"
    | "punctuation"
    | "mixed_language"
    | "other";
  behaviorSummary: string;
  functions: string[];
  variationPolicy: "exact_only" | "same_family" | "open_variation";
  examples: string[];
  useWhen?: string[];
  avoidWhen?: string[];
  density?: 0 | 1 | 2 | 3;
  status: "candidate" | "active" | "archived";
  pinned?: boolean;
  explicit?: boolean;
  lastSeenAt: string;
  archivedAt?: string;
  evidence: EvidenceState;
}

interface ScaleMemory {
  value: 1 | 2 | 3 | 4 | 5;
  latentMean: number;
  confidence: number;
  evidenceWeight: number;
  evidenceCount: number;
  sessionCount: number;
  lastUpdatedAt: string;
  pinned?: boolean;
}
```

完整 profile 至少包含：

- `observedVoice.verbosity: 1..5`：用户自己的表达长度。
- `observedVoice.formality: 1..5`：用户表达的正式程度。
- `observedVoice.expressiveness: 1..5`：用户自己的情绪外显强度。
- `observedVoice.rhythm`：例如短句、碎片式、完整段落、连续追加。
- `punctuation.baseStyle: minimal | standard | expressive | ellipses`。
- `punctuation.literalPatterns`：保留原样、`exact_only` 的特殊标点模式。
- `expressionPatterns`：行为摘要、功能、受控变体策略、例子和证据。
- `observedVoice.expressionDensity: 0..3`：表情类表达的总体密度统计，可由对应模式覆盖。
- `responsePreferences.replyVerbosity: 1..5`。
- `responsePreferences.warmth: 1..5`。
- `responsePreferences.initiative: 1..5`。
- `responsePreferences.supportMode`：例如先听、共情、共同梳理、直接建议。

`temperature` 不使用，避免与模型采样参数混淆。用户自己的情绪表达使用
`expressiveness`，希望 agent 给予的温度使用 `warmth`。

### 4.1 固定量表标签

存储层保留整数，渲染层按下表生成固定短标签，不让宿主 agent 临时自由解释：

| 字段 | 1 | 2 | 3 | 4 | 5 |
|---|---|---|---|---|---|
| 表达长度 | 极简短 | 偏简短 | 正常交流 | 喜欢展开 | 经常长篇展开 |
| 正式度 | 纯口语/网感 | 偏口语 | 日常沟通 | 偏书面 | 书面/官方 |
| 表达强度 | 克制/偏冷 | 较克制 | 适中 | 明显外显 | 强烈外显 |
| 回复长度 | 一句即可 | 偏简短 | 正常展开 | 较详细 | 充分展开 |
| 回应温度 | 冷静克制 | 偏理性 | 平和友好 | 温暖、有共情 | 高温暖与陪伴感 |
| 主动延展 | 不主动追问 | 少量延展 | 适当追问 | 主动陪聊 | 高主动延展 |

`observedVoice.expressionDensity` 固定为：

| 值 | 渲染标签 |
|---:|---|
| 0 | 不使用 |
| 1 | 极少使用 |
| 2 | 偶尔使用 |
| 3 | 频繁使用 |

这些标签是执行锚点，不是精确字数或每段表情数的硬指令。例如
`回复长度=3/5（正常展开）` 表示不刻意压缩、也不默认长篇铺陈，
仍允许根据当前内容复杂度自然变化。

## 5. 评分如何自然增减

### 5.1 两个数字层必须分开

- `value`：对 agent 可执行的 `1-5` 风格量表。
- `confidence`：系统对这个量表值的内部把握，范围 `0-1`，不注入给 agent。

不能因为某条消息很长，就直接把“表达长度”从 2 改成 4。内部应保留连续值
`latentMean`，对多条证据做加权滚动估计，只在跨过滞回门槛时改变对外 `value`。

### 5.2 证据来源与权重

| 证据 | 建议权重 | 用途 |
|---|---:|---|
| 用户明确绝对要求 | 1.00 | “以后就简短回”、“多安慰我一下” |
| 用户明确方向性反馈 | 0.90 | “短一点”、“再详细些”、“别急着给建议” |
| 多次重复的行为偏好 | 0.65 | 多次要求先共情或先结论 |
| 确定性规则统计 | 0.50 | 标点、表情密度、消息长度等 |
| 宿主 LLM 单次观察 | 0.30 | 正式度、表达强度、节奏等语义判断 |

权重是实验初值，最终常量必须通过 `E05` 校准，不得靠感觉直接固定。

### 5.3 滚动估计和滞回

- 每个可观察量表保留最近 50 条有效证据，而不是无限累积。
- 对离群值使用截尾均值或加权中位数，单条消息的最大影响受限。
- 普通观察使 `latentMean` 向新证据缓慢移动，不直接对整数 `+1/-1`。
- 当新均值高于当前整数 `0.65` 以上，且至少有 3 条一致证据、跨 2 个会话，才上调 1 级。
- 下调使用对称的 `-0.65` 门槛，不因为某个特征暂时没出现就降分。
- 一次普通观察最多使对外整数变化 1 级。
- 用户明确说“以后都……”时可直接设定目标值并标记 `explicit`；
  “短一点”这类方向反馈每次最多移动 1 级。
- 用户固定的量表不受普通观察改写，只能由用户新的明确要求或手动解除固定来改变。

### 5.4 可观察语感与回应偏好分别更新

`observedVoice`：

- 约 5 条有效消息后可形成内部暂定值。
- 约 12-15 条有效消息且跨至少 2 个会话后，才可成为稳定注入项。
- 标点、表情密度、消息长度优先用稳定统计。
- 正式度、表达强度和节奏可使用宿主 LLM 观察，但必须积累多条证据。

`responsePreferences`：

- 用户消息很短，不等于用户希望 agent 也很短。
- 默认行为由产品提供，证据不足时不冒充“已学习的用户偏好”。
- 用户明确反馈优先；无明确反馈时，需要重复、一致的行为证据才能激活。
- “回复长度=3/5”可作为产品默认，但未获得用户证据前不写入学习记录。

### 5.5 口癖、表达模式和翻车日志

- 首次发现具体原文时只增加低层例子证据；不能因一个颜文字就直接生成宽泛的 active 风格。
- 同一表达模式至少有 3 次实际观察且跨 2 个会话才自动激活；不同原文只有在
  `kind + functions` 匹配时才可共同支持一个模式。
- 缺席不是反证：用户连续几条没用某种表达，不减分。
- 明确说“别学这个”立即删除或封禁对应项，不再被同一条消息重建。
- 模式竞争排名考虑频率、跨会话数、新鲜度、功能清晰度和与普通填充词的区分度。
- 表达标记的密度由“含标记的有效消息占比”估计，而不是单纯累计符号数。
- 翻车日志只由用户明确纠正或用户确认的 review 结果产生，不从沉默推断。
- 翻车项应写成对 agent 可执行的禁止规则，不存储当时对话全文。

### 5.6 简单遗忘与容量控制

沿用现有 v0.4 的 `candidate -> active -> archived -> deleted` 生命周期，并采用常见记忆系统的
“重要程度、重复次数、最近出现”排序。不引入向量检索、LLM 总结式遗忘或每轮连续衰减；
cleanup 全部由 MCP 本地确定性执行，不增加 LLM token。

默认容量：

- brief：典型 2 个表达模式，硬上限 5 个；单条回复通常仍只自然使用其中 0-1 个。
- store：未固定项按状态分别为 `active` 最多 12 个、`candidate` 最多 24 个、`archived` 最多 24 个。
- store 总安全上限为 64 个表达模式，包括 pinned；达到上限后先清理未固定项。
  如果 64 个全部受保护，则拒绝新的自动候选并在 status 中报告容量，不得偷偷删除 pinned。
- 每个模式最多保存 3 个脱敏短例子，重复 literal 不占新槽位。

默认遗忘规则：

- `candidate` 连续 30 天没有新证据：删除。
- `active` 连续 180 天没有新证据：转为 `archived`，立即停止注入，但数据仍可恢复。
- `archived` 从最后一次出现起满 360 天仍没有新证据：删除。
- archived 模式重新出现时回到 `candidate`；只计算归档后的新证据，重新满足 3 次、2 个 session
  才恢复 active。用户明确确认可以立即恢复。
- pinned 永不被 TTL 或容量 cleanup 自动归档/删除；用户主动 `forget` 始终立即删除。
- `explicit` 不是永久保护，只提高容量排序；真正需要长期保留必须 pin。

容量超限时先执行 TTL cleanup，再按以下稳定顺序保留：`pinned > explicit > sessionCount > seenCount > lastSeenAt`。
未固定 active 超过 12 时，最低项进入 archived；candidate 超过 24 时删除最低的一次性候选；
archived 超过 24 时删除最低且最旧的项。排序最后使用稳定 id 打破平局，保证同一 store 重放结果一致。

该自动遗忘只作用于 `ExpressionPattern`。称呼、用户明确的陪伴偏好和翻车日志不能因“最近没出现”
被自动遗忘，只能由用户纠正、forget 或对应的显式管理流程修改。

v1 -> v2 迁移本身不得为了满足新容量而删除旧数据。迁移校验完成后允许暂时超限，
首次正常 cleanup 再按上述规则处理，并返回 archived/deleted/rejected 计数供审计。

### 5.7 宿主 agent 与 MCP 的职责边界

宿主 agent 不计算最终分数。观察通道和学习策略分开配置：

- **hook 通道（首选）**：宿主在模型外把每条最新用户消息交给 MCP。规则统计不产生
  LLM 工具调用 token；宿主模型只在明确反馈、纠正或高置信度语义信号出现时附加 hint。
- **agent 通道（通用 MCP fallback）**：由模型调用工具。冷启动若需要精确统计，必须暂时使用
  `full` 策略逐消息提交；记忆成熟后切到 `event`，只在明确反馈、纠正或明显表达模式/新例子
  实际出现时提交该条消息。`off` 只读取，不继续学习。

不调用就不会产生新证据，MCP 也不可能补算没见过的消息。可选的 session 末蒸馏只提交
0-3 个定性候选，每个候选最多算 1 次低权重观察，不能携带或伪造批量出现次数，也不能
绕过“3 次、2 个 session”的激活门槛。bootstrap/status 必须返回当前 `channel` 和 `policy`。

宿主持久指令保持短小：

```text
新 session 首次回复前读取 style brief。
按 bootstrap 返回的观察策略执行：full 时逐消息提交；event 时仅在明确反馈、纠正，
或疑似表达模式/新例子实际出现时提交这一条消息；off 时不学习。
不确定不猜测。评分、门槛和持久化由 MCP 处理。
```

职责分配：

- hook 通道或 agent+full 策略下，MCP 才能逐消息统计长度、标点 literal、表达标记密度和已知例子次数。
- agent+event 策略下，只有实际提交的消息参与统计；未提交消息不补算，session 末蒸馏不伪造频率。
- 宿主只报告少数语义项：回复长度、回应温度、主动延展、支持方式、称呼方向/纠正、
  `用户→助手` 称呼的短情绪/关系语境和翻车纠正。
- 称呼 hint 必须绑定当前用户消息并显式携带 `from/to`；情绪摘要限为一句可观察的话语作用，
  MCP 校验长度和来源，拒绝心理诊断、无方向 hint 和 assistant 输出形成的自我强化证据。
- 新表达的 `behaviorSummary/functions/variationPolicy` 可由宿主以紧凑 hint 提供；MCP 自己不能理解其语义。
- 宿主 hint 只是证据，不得直接写最终 `value` 或绕过激活门槛。
- 权重、滚动窗口、滞回、confidence、升降和持久化全部由 MCP 执行，不进入聊天 brief。
- 明确反馈需绑定当前用户消息；服务端校验枚举、范围和来源，并拒绝无法对应当前消息的高权重更新。

## 6. 注入时机与 token 控制

- 宿主在新会话开始时调用 `get_style_brief`。
- hook 通道在模型外逐消息观察；agent 通道按 bootstrap 返回的 `full/event/off` 策略调用，
  不把整份 brief 每轮重复注入。
- brief 带单调递增的 `revision`。revision 未变化时返回最小确认，不重复注入；普通变化优先返回 delta。
- 用户纠错、上下文压缩、用户要求重新对齐或 delta 无法独立执行时刷新完整 capsule。
- 长聊兜底刷新不得早于 30 个用户回合；是否需要更短间隔由 `E06` 用实际漂移证据决定。
- 渲染器对每段设数量上限：称呼每个方向最多 2 个且典型为 1 个，表达模式最多 5 个，
  特殊标点 3 个，翻车日志 3 条。
- 对同义指令合并，不同时输出内部分数、证据、时间戳和显示文案。
- 默认值、低 confidence 项和当前无关项不注入；典型 brief 默认选 2 个最有价值且互不重复的表达模式，
  每个只带 1 个例子。5 项上限和 capsule token 上限同时生效，先满足 token 上限；
  行为摘要通常比注入多个孤立原文更短，也更容易让 agent 自然泛化。

### 6.1 跨 session 自动启动与对齐

跨 session 不能依赖模型“记得上一次怎么做”，必须同时持久化三层配置：

1. **宿主 MCP 配置**：在宿主的全局 MCP 配置中注册稳定 launcher。宿主在新 session
   首次使用工具时自动启动服务，不要求用户手动运行常驻进程。
2. **固定 store**：所有属于同一用户/agent 的 session 使用同一个绝对
   `STYLE_MEMORY_PATH`；运行时升级、工作目录变化和 MCP 重启不得改变该路径。
3. **宿主持久指令**：把本节的短启动协议安装到宿主的全局 agent instruction，
   而不是只发在某一个聊天窗口里。

新 session 的固定协议：

1. 在第一条实质回复前调用 `get_style_brief`，把返回 brief 作为当前 session 的风格约束。
2. 为本 session 使用一个无语义的短 `sessionId`；优先使用宿主提供的 conversation ID，
   否则由启动工具生成。后续观察自动携带，不要求模型自己编造身份信息。
3. hook 通道由宿主自动逐消息观察；agent 通道冷启动需要精确学习时使用 `full` 逐消息调用，
   核心记忆成熟后使用 `event`，只在明确反馈、纠正、疑似表达模式或新例子实际出现时调用。
4. 明确纠错、新记忆激活或用户要求重新对齐时，同轮返回 delta 或刷新 capsule；
   revision 未变化时不重复返回正文。
5. session 结束不删除 store。新 session 再次启动时从同一路径读取已经激活的记忆。

MCP 协议本身不能主动把 brief 推入尚未调用它的模型上下文。因此“自动”必须由宿主的
持久 MCP 配置和全局指令保证。对支持启动 hook 的宿主，安装器应注册自动 bootstrap；
不支持 hook 的宿主使用首轮强制工具调用。若宿主既不支持持久指令也不保证首轮调用，
安装器必须明确报告该接入只能 best-effort，不能宣称已保证跨 session 对齐。

默认 `3/5` 且没有用户证据的字段不写入学习记录，也不必注入。只有 active、explicit
或 pinned 的结论进入 brief；完整评分规则和证据历史永不进入聊天上下文。

### 6.2 运行时工具面与总成本

默认聊天连接不能暴露全部管理工具。实现时至少提供两种工具面：

- `runtime`：最多 3 个紧凑工具，用于 bootstrap/sync、事件更新和明确纠错。
- `admin`：list、review、pin、forget、诊断和迁移等低频工具，仅在管理记忆时启用。

`observe/sync` 的日常成功返回应保持为最小机器结果，例如 `{"ok":1,"refresh":0}`；
不得默认返回完整 learned/updated 对象。只有 `refresh=1` 时返回短 delta 或要求获取新 capsule。
`sessionId` 优先由宿主元数据自动携带；必须由模型传递时使用短、不含语义的 handle。

各环节成本必须分开报告：

| 环节 | 是否增加 LLM token | 说明 |
|---|---|---|
| store 持久化、计数、滚动评分 | 否 | MCP 本地计算，不调用模型 |
| 模型外 hook 提交原消息 | 否 | 只增加本地 I/O；原消息本来就在对话中 |
| 宿主语义 hint | 是 | 仅在新模式、明确反馈或无法匹配的新例子出现时生成；不得每轮生成 |
| runtime 工具 schema | 是 | 工具暴露给模型时通常每轮占输入；因此最多 3 个且字段要短 |
| `agent+full` 工具调用 | 是 | 冷启动逐消息产生参数和返回 token，只在无 hook 且确需精确学习时使用 |
| `agent+event` 工具调用 | 是，但低频 | 只有事件回合产生调用参数/返回；schema 成本仍单独存在 |
| style capsule / delta | 是 | capsule 在当前上下文中会继续占后续回合输入；revision 不变只是不再添加重复副本 |

行为模式本身不会让学习阶段凭空多一次 LLM 调用。语义不清的新模式才需要一个紧凑 hint；
已知例子的计数、阈值和持久化仍由 MCP 完成。典型 capsule 默认只放一个表达模式且只带一个例子，
单行成本由 `E06` 用目标 tokenizer 实测，不先用中文字数冒充 token 数。

`E06` 对一个固定 20 回合对话统计：持久 agent 指令、每轮工具 schema、工具调用参数、工具返回、
首次 capsule、后续每次模型输入中仍保留的 capsule，以及刷新 delta。必须读取实际 API usage；
若提供方报告 cached input，应同时记录总 input、cached input 和实际计费口径，不能把缓存 token 当不存在。
目标是在关键行为通过的方案中使总成本最小，不能用缩短 brief 掩盖每轮 schema 或额外模型往返。

## 7. 可安全替换的升级契约

`v0.5.0` 安装给已有 agent 时，必须自动替换旧运行时，同时保留用户的 store 和连接配置。

必须实现：

1. 稳定启动入口：宿主配置指向不随版本变化的 launcher，真实运行时放入版本目录。
2. 分阶段安装：先在 staging 目录安装、构建、测试和自检，不原地覆盖正在运行的版本。
3. 备份：在切换前备份旧运行时、已发现的 MCP 配置和 store。
4. store 迁移：在副本上执行 `v1 -> v2`，校验后才原子替换；失败时旧 store 不变。
5. 原子切换：同一文件系统内使用 rename/symlink 切换 launcher 目标，中途不得出现半安装状态。
6. 版本握手：启动后 `get_style_memory_status` 能返回 server/store schema 版本，安装器据此确认新版本已连接。
7. 宿主重连：对可自动重连的宿主执行重连；无法程序化重连时返回明确、有限步骤，不假装已完成。
8. 幂等：对同一版本重复执行安装不应累加配置、重复迁移或丢失 store。
9. 并发锁：两个安装进程同时运行时只有一个获得切换权，另一个安全退出或等待。
10. 回滚：构建、迁移、切换、启动或握手任意一步失败都能回到上一个已验证版本。

## 9. 必须实验

### E01 称呼方向

数据集至少包含：多个“用户对助手的称呼”、多个“用户要求助手对用户的称呼”、同一 literal
同时合法存在于两个方向、单方向纠正/forget、亲昵/玩笑/寻求靠近等可观察情绪语境、
无足够情绪证据的中性语境、assistant 自己输出的昵称，以及引用、转述、否定、反例、
第三方姓名、角色名、文档示例、环境文本和工具输出。

实验分三层执行，证据不得混写：

1. **确定性层**：表驱动 fixture 明确 `sourceRole/message/expectedDirection/expectedStoreDelta`，
   不调用 LLM，验证 schema、方向键、容量、激活、双向同 literal 和独立纠错。
2. **语义 hint 层**：使用至少 60 条带标注的当前消息输入两种目标宿主 agent，亲昵、玩笑、
   寻求靠近、尊重、中性和无法判断各至少 10 条；验证 MCP 只接受短的可观察摘要，
   无法判断时落到中性而不是心理诊断。
3. **生成层**：把同一组最终 capsule 交给至少两种目标 agent；使用固定场景检查是否反称、
   是否只使用 `助手→用户` 项，以及能否理解 `用户→助手` 摘要但不机械复述摘要。

通过条件：

- 所有标注 fixture 的方向分类准确率 100%，非法 `from/to` 组合被拒绝。
- 两方向可各保存多个值；同一 literal 在两个方向中具有独立 id、状态、证据和摘要。
- 修改、确认、pin、archive 或 forget 任一方向时，另一方向的同 literal 字节级不变。
- 引用、转述、否定、第三方/角色名称、文档/环境/工具文本不进入称呼 store。
- assistant 自己使用昵称不会创建或增强 `助手→用户` 记录。
- `用户→助手` 每个 active 渲染项有一句短的可观察情绪/关系语境或中性摘要；
  对有标注的语境，摘要语义与标注一致，不出现心理/人格诊断。
- 两种目标宿主 agent 的 `affectSummary` 与人工标签语义一致率均 >=90%；“无法判断”样本中
  中性摘要/拒绝猜测率 >=95%，所有样本中心理/人格诊断为 0。记录原始输出和判定依据供复核。
- `用户→助手` 的称呼在至少两种目标 agent、每种至少 10 个诱导回复中反称次数为 0；
  `助手→用户` 只在对应 `useWhen` 合适时使用。
- store 每方向不超过 6 个，brief 每方向不超过 2 个；典型 profile 每方向为 1 个。
  满容量时自动候选被明确拒绝，既有称呼不被静默淘汰。

### E02 观察与偏好分离

构造“用户说得短但要求 agent 详细”、“用户情绪克制但需要温暖回应”等对照组。

通过条件：`observedVoice` 和 `responsePreferences` 分别更新，无交叉覆盖。

### E03 口癖与表达模式自然性

为每个模式提供行为摘要、功能、变体策略、实际例子、正例、反例和不相关对话。
至少包含颜文字 `same_family`、固定口头禅 `exact_only` 和一种 `open_variation`，
并使用至少两种目标 agent 生成回复。

通过条件：

- 一条实际提交的用户消息中同一模式最多增加 1 次观察；首次进入 candidate，至少 3 次实际观察且
  跨 2 个 session 才自动进入 active。用户明确确认/固定可走显式通道立即生效。
- 未提交给 MCP 的消息不计数；session 末蒸馏候选最多贡献 1 次低权重观察，不能提交批量 count。
- `same_family` 在合适情境中能自然使用至少一个用户从未出现过、但类型/功能/强度匹配的变体。
- 不机械重复最近观察到的原文；连续 5 条合适回复中不得只复读同一个例子。
- 不得扩展到功能不符、强度突变、密度更高或不同类型的无关表达。
- `exact_only` 只能使用记录原文，特殊标点的字符序列保持不变。
- 不相关情境中不强行使用。
- 单条回复通常不超过 1 个高辨识度表达模式。
- 仅有文档示例、用户未实际表达的口癖不得被学习。
- 当 store 有 8 个相关 active 模式时，典型 brief 稳定选择 2 个；允许完整展示时也不得超过 5 个，
  且当前情境变化后能选择新的相关项，不固定霸占同一组。

### E04 标点与表达标记往返

覆盖 emoji、组合 emoji、颜文字、Unicode 符号、文本式表情、未知类型、三种 `variationPolicy` 及
`。。。`、`...`、`……`、`?!`、`？！`、`~~`。

通过条件：模式语义、功能、变体策略和例子在存储、迁移、重载后不丢失；
所有 `exact_only` 例子的原文字节/字符序列不变，未知类型不丢失。

### E05 评分增减校准

建立标注数据集，包含稳定用户、单条离群消息、长期渐变、明确绝对要求、方向反馈、
互相矛盾的反馈和跨会话数据。

通过条件：

- 单条离群消息不改变对外整数量表。
- 稳定风格在 12-15 条有效消息、跨 2 个会话后能稳定到目标值±1。
- 持续转变只在满足证据数和滞回门槛后变化，无抖动往返。
- 明确要求可立即或单步生效，不被后续低权重观察迅速冲掉。
- 口癖缺席、表情缺席和普通默认回合不被当作反证。

### E06 brief 可执行性与 token

对空 profile、典型 profile、全上限 profile和冲突 profile，分别生成完整六段、active-only
紧凑六段和“紧凑 capsule + delta”三种版本，使用至少两种目标 agent 检查执行。

通过条件：

- 顺序与六段契约一致，空段省略。
- 所有量表均为“数值+语义标签”，无裸数字。
- 典型首次 capsule <= 120 tokens，全上限 <= 240 tokens，普通 delta <= 30 tokens；
  记录目标模型实际 tokenizer，并继续选择低于上限且行为达标的最短版本。
- 典型表达模式 2 个、硬上限 5 个；如果 5 个模式使 capsule 超过 token 上限，必须减少条目，
  不能为了凑满数量突破 token 预算。
- agent 能正确区分两个方向：用户对它的称呼不能反称；只有 `助手→用户` 项可称呼用户；
  同时能根据用户→助手的短情绪语境理解该称呼的关系作用，并根据行为摘要和变体边界选择合适表达。
- 对比“多个孤立原文”和“一个行为模式 + 一个例子”的 token 与生成结果；行为模式方案必须在自然泛化、
  不机械复读和不越界上通过。孤立原文方案若未通过行为门槛，不得仅因更短而胜出；
  所有通过方案中选择总 token 最少者。
- 紧凑方案在称呼、明确偏好执行、口癖自然性和跨 session 稳定性上不得劣于完整方案；
  若多个方案通过，选择固定 20 回合总 token 最少者。
- 20 回合总成本必须计入实际每轮 input/output、工具 schema、参数、返回、capsule 和 delta；
  capsule 留在上下文中的后续 input 不能漏算，revision 不变时不得再追加正文副本。
- 对比 `hook+full`、`agent+full`、`agent+event` 和 `off`，记录模型调用轮次与 token；
  默认选择 hook，无法接入 hook 时按核心记忆成熟度选择通过稳定性门槛的最低成本策略。

### E07 纠错与翻车防复发

模拟“别叫我 X”、“这是我叫你的”、“别学这个口癖”、“我只是引用别人”和
“别急着给建议”；另加同一 literal 双向并存后只纠正/forget 一个方向的用例。

通过条件：同轮立即生效，旧错误项不注入，同一条用户消息不将已删除内容重建；
单方向纠错后另一方向的同 literal、摘要、状态和证据完全不变。

### E08 v1 -> v2 迁移

使用 v0.1/v0.4 store fixture、缺字段 store、未知字段 store、部分损坏 store、无法确认方向的
legacy 称呼/昵称和重复执行迁移。

通过条件：可迁移数据 100% 保留，反复执行结果一致，失败时原文件哈希不变，备份可恢复；
无法确认方向的 legacy 值不会被猜成可直接称呼用户的 active `助手→用户`，也不会凭字面生成情绪诊断。

### E09 并发、损坏与敏感信息

并发提交观察和反馈，注入截断写、无效 JSON、超长文本、密钥/PII、异常 Unicode、巨大标记列表，
并用可控时钟构造 30/180/360 天边界、容量超限、全 pinned 和归档后重新出现。

通过条件：

- 无丢更新、无敏感信息落盘、无不受限增长，损坏后能进入可解释的恢复路径。
- 30/180/360 天边界分别执行 candidate 删除、active 归档和 archived 删除；边界日前不提前处理。
- pinned 不受 TTL 和容量淘汰；用户 forget 仍立即删除。
- 未固定的 active/candidate/archived 默认容量分别稳定在 12/24/24，总安全上限为 64；
  全部受保护时拒绝自动学习并返回明确容量状态。
- 超限排序按 `pinned > explicit > sessionCount > seenCount > lastSeenAt > stableId` 可重复产生同一结果。
- archived 重新出现后只使用归档后的新证据，未满 3 次、2 个 session 不恢复 active。
- v1 -> v2 迁移不因新容量直接删除旧数据，首次 cleanup 的变更有计数且可审计。

### E10 自动替换与回滚

从真实 `v0.4.0` 安装开始，分别在构建、store 迁移、配置写入、原子切换、server 启动和版本握手注入失败。

通过条件：

- 正常路径自动替换旧运行时，保留 store 和宿主配置。
- 同版本连续安装 3 次结果幂等。
- 两个安装进程并发时只有一个成功切换，无交错状态。
- 每个故障点都保留可运行旧版本，原 store 哈希不变，回滚后握手通过。
- 安装器不能仅因为文件复制成功就报告完成，必须校验运行时和 store schema 版本。
- 连续新建至少 3 个隔离 session，均无需手动启动 MCP，首轮从同一 store 取得一致的 active brief；
  每个 session 的证据 ID 可区分，且任何 session 都不会把完整规则或证据历史注入上下文。
